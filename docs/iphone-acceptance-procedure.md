# Physical iPhone acceptance procedure

The automated baseline covers shared backend operations; it does not establish physical-device acceptance.

1. The owner must review working days/hours, timezone, service area, travel buffer, daily capacity and service durations in the existing owner dashboard. Save only values the owner has approved. Current staging blocks confirmations while hours/service area remain unconfirmed.
2. Verify the controlled IPA, embedded profile, certificate and production aps-environment with the strict archive verifier. Keep the existing distribution identity and DocDetailing profile. Preserve the archive, dSYMs, full build logs, test JSON and checksum manifest.
3. Supply an authorized backend APNs auth key and Key ID securely outside Git. The registered team is UDDPKPR3CJ; the topic is com.docincorporated.docdetailing; App Store/TestFlight uses production APNs. Set TEST_NATIVE_OWNER_IDS to verified isolated owner IDs, never an unrestricted recipient list.
4. Keep COMMUNICATIONS_MODE=disabled and all ALLOW_*_SEND flags false until explicit activation approval. Customer email also requires a verified sender and provider credentials. An App Store Connect API key is not an APNs provider key.
5. Obtain explicit approval for a controlled tester-only Apple upload/install route after archive verification. No Apple upload has been performed by this work. Physical delivery requires an installed signed app; TestFlight readiness cannot be claimed from a simulator or provider acceptance.
6. Sign in as Joseph using his existing private test account. Verify Keychain restoration after closing/reopening the app; revoke the session from another authorized owner session and verify that private screens close. Repeat logout while offline; local private access must clear. If server revocation could not be delivered offline, revoke connected sessions separately.
7. Deny notification permission and confirm that the app stays usable and explains the state. Enable permission through the app/iPhone settings, resume, and verify one renewed owner/business device registration. Test opt-out and sign-out. A notification already accepted by Apple may remain visible; tapping must still require authorization.
8. After approved test-only APNs activation, submit an isolated website booking. Verify the correct persistent inbox entry and unread count. Repeat with the app foregrounded, backgrounded, and terminated. Tap each alert and verify the exact booking, tenant, customer and appointment; repeat a tap to test deduplication.
9. Confirm a booking in the app; verify the website/private customer link and calendar update. Submit an overlapping request and verify server conflict prevention. Propose another time and revised total; accept via the private customer link and verify the app, calendar and history. Customer confirmation email must be tested only with separately approved recipients and activation.
10. Customer reschedule-request backend/native handling is implemented and tested. Adding its form to the existing website is pending explicit approval after automatic review blocked that website change. Until approved, this specific website entry point is not complete.
11. Create a customer with two vehicles and inspect service history. Open a job, add approved services/charges, record labor/travel, count inventory, consume a fractional quantity, and confirm the remaining stock/cost. Record each direct cost once; do not repeat the same material/labor/travel cost on a service line.
12. Capture/select before/after photographs, including an actual iPhone HEIC library image. Verify orientation, optimized upload, private access and invoice selection. Existing library originals stay on the phone; the camera picker is not claimed to save an original to the library automatically. Direct browser HEIC decoding still needs hosted acceptance.
13. Complete the job and create its invoice. Check services/materials, discount, tax, photos and review link. Record a cash deposit/partial payment and external balance payment with tip. Verify paid status, receipts, native PDF share/cancel, quarterly business-timezone cash report and job margin.
14. Rerun encrypted restoration into a fresh isolated D1/R2 target. Verify bookings, customer/vehicle data, settings, job costs, stock balances/movements, financial ledger and exact media bytes. Restored sessions must be absent, domains detached and notifications/device registrations held. Off-machine storage activation still requires the separately authorized independent destination and credentials.

No step authorizes public bookings, production DNS, commercial billing, Square activation, changes to another Doc application, certificate replacement or a public App Store submission.
